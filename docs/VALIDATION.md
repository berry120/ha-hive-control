# Validation and device coverage

## Automated checks

Version 0.5.0 validation on 5 November 2026: **134 Python tests passed**, **33 browser tests passed**, and Python lint, formatting and JavaScript syntax checks passed. Both GitHub Actions workflows passed actionlint validation; the standalone preview was checked in Chromium.

- Python tests run the controller against a simulated receiver and the transport against real zigpy 2.3.0 cluster serializers.
- Wire checks cover one-frame boost, the enum8 hold type, no manufacturer header on standard commands, holiday manufacturer code 4153, date/string/minute/temperature encodings and schedule command namespaces.
- Behaviour checks cover all returned write statuses, missing acknowledgements, readback mismatches, stale day revisions, Off preservation, input validation, device limits, serialization, ambiguous mode combinations and incomplete reads. Holiday creation requires a fresh disabled flag; enabled or unknown flags prevent writes. Cancelling permits a new holiday, and disabled holidays ignore unused date fields.
- Grouped schedule checks cover seven individual day reads, incomplete weeks, revision checks before any group writes, selected-day saves, preserved Off periods and stopping with a truthful partial result after a later day fails.
- Clock checks cover the Zigbee UTC epoch, conversion from Home Assistant's time zone, ambiguous/nonexistent DST times, advancing-clock readback, rejected or unconfirmed writes, signed differences calculated against the HA server's clock, and writing only the Time attribute with the UTC wire type and no application retries.
- Settings checks cover persistent boost targets, the 30°C default, validation, preserving device availability when saving, updating settings without restarting receiver operations, and the one-time migration of the old 19°C default while keeping other custom targets.
- Browser tests exercise the actual custom elements in headless Chromium with a simulated Home Assistant service API. Coverage includes grouped patterns, applying a pattern to all days, splitting out one day, partial-read and partial-save handling, preserved drafts, the three heating modes, saved boost targets, one holiday temperature input per state, and cancelling before planning another holiday. Clock checks cover the inclusive 2/5-minute colour thresholds in both directions, automatic refresh on re-entry, no stale green status after failed reads or unconfirmed writes, and the compact input with Set to its right. Card configuration, escaping, multiple installations, unavailable state, mobile layout, dark mode and keyboard dismissal are also covered.
- New-pattern checks cover creating an independent day or group, copying existing times, leaving unselected days untouched, adding/removing periods within the one-to-six limit, and preventing submission with incomplete fields. Header refresh checks cover all four tabs, pending-operation disabling, preserved form inputs, and refusing to discard an edited schedule. Layout checks cover labels to the right of values at matching font sizes and spacing before the holiday form.
- Availability checks cover sensor setup with no successful first read, suppressing cached attributes after failure, passive ZHA wall-thermostat availability, missing devices, gateway reloads and subsequent recovery. Backend checks exercise the production setup, coordinator and sensor declarations with simulated HA boundaries; they do not run a full HA instance. Browser checks cover unavailable, unknown, restored and missing sensors, lost HA connections, automatically selected cards, hidden cached temperatures/countdowns, disabled heating actions and automatic recovery in an open dialog.
- Source checks confirm the Home Assistant 2026.10.4 symbols used for ZHA device access, frontend registration, service responses, config-entry-only setup and authorization. These are source compatibility checks, not a running HA integration test.
- Package checks validate action schemas against probatio 0.13.0, their dashboard payloads, services metadata and config-flow translations. Setup requires two distinct device addresses with no defaults; existing saved addresses are preserved. The archive contains no test dependencies or caches.
- Distribution checks confirm the fixed ZIP/preview filenames and repeatable ZIP output despite changed source timestamps or line endings. Publishing tests use temporary local Git repositories to check that only the two distribution files are committed, unchanged builds produce no commit, stale builds and existing staged work are rejected, concurrent source pushes are preserved, and denied pushes report the permission problem.

The separate PR and `main` workflows run the same checks; only the `main` workflow publishes successful builds. Their GitHub-hosted execution and repository permissions can only be confirmed after the repository is pushed to GitHub. Local publisher tests do not contact a hosted repository.

2. Compare the temperature and relay state with ZHA and the wall thermostat.
3. Start the default 10-minute/30°C boost, cancel to schedule, and confirm physical display and receiver state. Change its target in Settings, restart HA, and confirm the saved target is used by both boost buttons. Let a separate boost expire normally.
4. Read the week, change one transition on a selected group, save it and compare every selected day with the wall thermostat; restore the originals if this was a test.
5. Confirm holiday temperature, creation and cancellation. Inspect all dates and the flag physically and subsequently verify execution at the configured time.
6. Observe the system through real schedule transitions, network interruption, HA restart and ZHA reload. Start HA while the receiver is offline; confirm the card shows **Thermostat unreachable** without cached temperatures, then recovers when the pair becomes available. Check wall-thermostat loss separately using ZHA's battery-device availability timeout.
7. Read and set the receiver time, including a summer date, and compare both receiver readback and the wall display. Existing timezone/DST settings and time-server flags are preserved; devices may reject writes to a clock they own as a time master.

The protocol reference explicitly leaves frost-threshold mapping, child-lock mapping, holiday creation semantics and daylight-saving behaviour unresolved. No test in this repository establishes those missing physical behaviours.
